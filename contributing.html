Contributing

Omnitrix is developed in four repositories:

RepositoryPackageContains
omnitrixomnitrix/omnitrixthe application template
omnitrix-coreomnitrix/corethe framework (Omnitrix\) and the engine (Omnitrix\Core\)
omnitrix-installeromnitrix/installerthe omnitrix new command
omnitrix-docs—this documentation site

Requirements​

PHP 8.3+ with ext-openswoole 26.2+, ext-pdo_mysql (mysqlnd) and ext-redis 6.3+, Composer 2, OpenSSL, and MariaDB 11+ and Redis 7+ binaries on the PATH for the integration tests.

Running the test suites (omnitrix/core)​

composer install
bin/services up        # MariaDB on 127.0.0.1:33306 and Redis on 127.0.0.1:63790, data in var/
make check             # composer validate/audit, coding standards, static analysis, all tests
bin/services down

bin/services starts both servers as unprivileged processes; no containers or root access are needed. To use other servers, export the variables listed in .env.example.

Target
make lint / make lint-fixPHP-CS-Fixer check / fix
make stanPHPStan, level max with strict rules
make test-unit, make test-integration, make testPHPUnit suites

Tests run inside an OpenSwoole coroutine with runtime hooks enabled (bin/omnitrix-phpunit); do not run vendor/bin/phpunit directly. Engine tests are in tests/Core, framework tests in tests/Framework.

Developing packages together​

To try changes to omnitrix/core in an application, point Composer at your checkout without committing the change:

composer config repositories.omnitrix-core '{"type": "path", "url": "../omnitrix-core", "options": {"symlink": true, "versions": {"omnitrix/core": "0.1.0"}}}'
composer update omnitrix/core
# ...
git checkout composer.json && composer update omnitrix/core

To try the full installation from local checkouts, pass the repositories to the installer; they are added to the new project:

omnitrix new demo \
  --repository='{"type":"path","url":"../omnitrix","options":{"versions":{"omnitrix/omnitrix":"0.1.0"}}}' \
  --repository='{"type":"path","url":"../omnitrix-core","options":{"versions":{"omnitrix/core":"0.1.0"}}}'

Conventions​

  • The engine (Omnitrix\Core\) never uses the framework layer (Omnitrix\). The framework uses only the engine's documented public types; anything marked @internal may change without notice.
  • Every change comes with tests. Integration tests use real services, never mocks of them.
  • Behaviour that depends on OpenSwoole or extension details gets a test and an entry in Platform notes; significant design decisions get a decision record.
  • Update this documentation and the package's CHANGELOG.md with user-visible changes. Regenerate the API reference with npm run api in the docs repository.
  • Commit messages: imperative mood, a short summary line, details in the body when useful.

Test conventions​

  • Non-blocking claims are proven, not assumed: overlap is measured with known delays, and a sibling coroutine must keep ticking while the operation under test waits.
  • Integration tests use real services, never mocks of them, and clean up the keys, tables and processes they create.
  • Server fixtures are started as child processes on free ports and stopped with SIGTERM, so graceful shutdown is exercised on every run.
  • TLS fixtures generate throw-away certificates with tests/Fixtures/tls/make-certs.sh.

Documentation site​

cd docs
npm install
npm start          # live preview on http://localhost:3000
npm run build      # static site in build/
